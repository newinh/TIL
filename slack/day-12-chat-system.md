# System Design Daily

## Day 12/40: 실시간 채팅은 연결보다 순서가 어렵다

### 오늘의 질문

- 메시지를 WebSocket으로 전달했다면 채팅 시스템의 핵심 문제는 해결된 걸까요?

### WHY: 연결은 통로일 뿐이다

채팅은 메시지가 빠르게 도착해야 하지만, 빠르기만 해서는 부족합니다. 사용자는 여러 기기에서 같은 대화를 보고, 오프라인 동안 쌓인 메시지를 다시 받아야 하며, 같은 대화 안에서는 순서를 이해할 수 있어야 합니다.

WebSocket은 양방향 연결을 오래 유지해 폴링 낭비를 줄입니다. 하지만 서버가 재시작되거나 네트워크가 끊기면 연결은 사라집니다. 메시지의 진짜 기록은 별도 저장소에 남아야 하고, 클라이언트는 자신이 어디까지 읽었는지 알아야 합니다.

### WHAT: 상태가 있는 연결 계층과 영속 메시지 계층

시스템을 두 영역으로 나눕니다.

- API 서버는 로그인, 프로필, 그룹 관리처럼 짧은 요청을 처리합니다.
- Chat Server는 WebSocket 연결을 유지하고 메시지를 전달합니다.
- Key-Value Store는 채팅 기록을 영구 보관합니다.
- Presence Service는 heartbeat로 온라인 상태를 계산합니다.
- Notification Service는 오프라인 사용자에게 푸시 알림을 보냅니다.

Chat Server는 상태를 가집니다. 어떤 사용자가 어느 서버에 연결됐는지 Service Discovery가 추적해야 합니다. 새 연결은 지역과 서버 용량을 고려해 배정하고, 서버를 내릴 때는 새 연결을 막은 뒤 기존 연결이 빠져나가게 해야 합니다.

### HOW: 대화 안에서만 순서를 보장한다

전 세계 모든 메시지에 완전한 순서를 매길 필요는 없습니다. 서로 관계없는 두 대화의 순서는 사용자에게 의미가 없습니다. 일대일 대화나 그룹 채널 안에서 증가하는 `message_id`면 충분합니다.

```text
(channel_id, message_id) -> message body
(user_id, device_id) -> cur_max_message_id
```

메시지 흐름은 다음과 같습니다.

1. 발신자가 Chat Server에 메시지를 보냅니다.
2. 서버가 대화 범위의 ID를 발급하고 저장소에 먼저 기록합니다.
3. 수신자가 온라인이면 연결된 Chat Server로 전달합니다.
4. 오프라인이면 나중 동기화할 수 있게 기록을 남기고 푸시 알림을 보냅니다.
5. 각 기기는 `cur_max_message_id`보다 큰 메시지를 요청합니다.

전달과 저장의 순서를 바꾸면 장애 때 메시지를 잃을 수 있습니다. 저장 전에 전달했는데 서버가 죽으면 수신 화면에는 보였지만 기록에는 없는 메시지가 됩니다. 저장 후 전달을 기본으로 두고, 클라이언트는 중복 수신을 견디도록 메시지 ID로 중복을 제거합니다.

### 그룹 채팅과 온라인 상태

소규모 그룹은 메시지를 각 사용자의 동기화 큐에 복사하면 읽기가 단순해집니다. 그러나 그룹이 커질수록 쓰기 증폭이 커집니다. 멤버 수가 제한된 그룹과 대형 공개 채널은 같은 모델로 다루지 않는 편이 낫습니다.

온라인 상태는 마지막 heartbeat 시각에서 계산합니다. 연결이 잠깐 흔들렸다고 즉시 오프라인으로 바꾸면 상태가 깜빡입니다. 일정 유예 시간을 두고, presence는 강한 일관성보다 최신성과 가용성을 우선합니다.

### 실패 모드

재연결 직후 실시간 전달과 과거 동기화가 겹치면 같은 메시지가 두 번 올 수 있습니다. 수신 기기는 ID로 병합해야 합니다. Chat Server 장애 때 Service Discovery 정보가 늦게 갱신되면 죽은 서버로 전달을 시도할 수 있으므로 실패한 전달은 저장소 기반 동기화로 복구합니다.

### 함정 체크

- WebSocket 연결 자체를 메시지 저장소처럼 취급하면 재연결 때 기록을 복구할 수 없습니다.
- 전역 순서 보장은 비용만 늘리고 사용자가 필요로 하는 대화별 순서를 놓칩니다.
- heartbeat 한 번 누락으로 오프라인 처리하면 모바일 네트워크에서 상태가 계속 흔들립니다.
- 푸시 알림 성공을 메시지 전달 성공으로 보면 안 됩니다.

### 오늘의 한 문장

> 채팅의 신뢰성은 연결이 아니라 영속 기록, 대화별 순서, 재동기화 경계에서 나옵니다.

### 30초 확인 문제

사용자가 휴대폰과 노트북을 동시에 사용합니다. 노트북이 이틀간 오프라인이었다가 다시 연결됐습니다. 누락 메시지를 어떻게 찾을까요?

### 정답과 해설

노트북이 마지막으로 처리한 대화별 `cur_max_message_id`를 서버에 보냅니다. 서버는 같은 수신자와 채널에서 그 ID보다 큰 메시지를 반환합니다. 실시간으로 동시에 들어온 메시지와 겹칠 수 있으므로 클라이언트는 `message_id`로 중복을 제거합니다. 서버 연결 이력만으로 복구하면 Chat Server 교체나 장기 오프라인을 처리할 수 없습니다.
