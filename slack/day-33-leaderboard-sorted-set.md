# System Design Daily

## Day 33/40: 실시간 순위표는 정렬 비용을 쓰기 때 지불한다

### 오늘의 질문

- 2,500번의 점수 갱신이 매초 들어오는 상황에서 상위 10명과 내 순위를 모두 실시간으로 보여 주려면 어떤 자료구조가 필요할까요?

### 왜 일반 테이블만으로는 부족한가

관계형 데이터베이스에 `user_id`, `score`를 저장하고 점수 인덱스를 만들면 상위 10명은 구할 수 있습니다. 하지만 임의 사용자의 순위를 구하려면 그 사용자보다 점수가 높은 행 수를 세어야 합니다. 수천만 명이 참여하고 점수가 계속 바뀌면 인덱스 갱신과 순위 집계 비용이 커집니다.

순위표의 핵심 쿼리는 네 가지입니다.

- 사용자의 점수를 원자적으로 증가시킨다.
- 상위 K명을 읽는다.
- 한 사용자의 순위를 읽는다.
- 한 사용자 주변 순위를 읽는다.

Redis Sorted Set은 이 접근 패턴을 그대로 제공합니다. 해시 테이블로 사용자와 점수를 연결하고, Skip List로 점수 순서를 유지합니다. 갱신할 때 `O(log N)`의 정렬 비용을 지불하는 대신 읽을 때 다시 전체를 정렬하지 않습니다.

### 필요한 Redis 연산

월별 토너먼트라면 키를 기간에 따라 분리할 수 있습니다.

```redis
ZINCRBY leaderboard:2026-08 1 user:1934
ZREVRANGE leaderboard:2026-08 0 9 WITHSCORES
ZREVRANK leaderboard:2026-08 user:1934
```

내 순위가 361위라면 주변 네 명씩 다음처럼 읽습니다.

```redis
ZREVRANGE leaderboard:2026-08 356 364 WITHSCORES
```

`ZINCRBY`는 사용자가 없으면 0에서 시작하고, 있으면 원자적으로 증가시킵니다. 애플리케이션에서 먼저 읽고 1을 더해 쓰는 방식은 동시에 승리한 요청이 서로의 갱신을 덮을 수 있습니다.

### 점수 갱신은 누가 호출해야 하나

클라이언트가 순위표 서비스에 직접 점수를 보내면 프록시로 요청을 바꿔 치팅할 수 있습니다. 게임 서버가 경기 결과를 검증하고 순위표 서비스를 호출해야 합니다.

```text
클라이언트 -> 게임 서버 -> 결과 검증 -> 순위표 서비스 -> Redis
```

경기 결과를 분석, 보상, 알림 서비스도 소비해야 한다면 검증된 승리 이벤트를 메시지 스트림에 발행할 수 있습니다. 단순히 순위표 하나만 필요하다면 큐를 먼저 넣지 않아도 됩니다. 요구가 없는 비동기 계층은 장애 지점과 운영 비용만 늘립니다.

### 동점 규칙을 먼저 정해야 한다

제품이 말하는 순위와 자료구조가 말하는 순위가 다를 수 있습니다. Redis의 rank는 멤버마다 위치를 하나씩 부여합니다. 같은 점수에 같은 순위를 주는 dense rank나 competition rank가 필요하다면 별도 규칙이 필요합니다.

예를 들어 먼저 달성한 사용자를 앞세우려면 점수와 달성 시각을 조합한 정렬 규칙을 만들 수 있습니다. 그러나 부동소수점 score에 여러 값을 억지로 압축하면 정밀도 문제가 생깁니다. 사용자에게 보여 줄 공식 순위 규칙, 동점 표시, 보상 경계에서의 처리 방식을 API 계약으로 정해야 합니다.

### Redis만 진실의 원천으로 두지 않는다

Redis는 빠르지만 메모리 장애와 운영 실수에 대비해야 합니다.

- 복제본과 자동 장애 전환을 둡니다.
- AOF나 Snapshot의 데이터 손실 범위를 정합니다.
- 검증된 경기 결과를 내구성 있는 저장소에 기록합니다.
- 장애 후 경기 결과 로그를 재생해 순위표를 재구축합니다.

사용자 이름과 프로필은 관계형 데이터베이스에 두고 상위 10명의 프로필만 캐시할 수 있습니다. 순위 계산과 프로필 조회를 한 저장소에 억지로 넣지 않습니다.

### 용량과 성능을 계산해 본다

월간 참여자 2,500만 명, 사용자 ID와 점수가 최소 26바이트라고 해도 원시 데이터는 약 650MB입니다. 실제 Redis는 객체와 Skip List 오버헤드를 더 쓰므로 실측이 필요하지만 단일 현대 서버에 들어갈 가능성이 큽니다. 예상치만 보고 샤딩부터 하지 말고 `redis-benchmark`와 실제 ID 길이, 복제, Snapshot 시 메모리까지 측정해야 합니다.

### 함정 체크

- 상위 10명 조회가 빠르다고 임의 사용자의 순위 조회도 빠른 것은 아닙니다.
- `GET`, 계산, `SET`으로 점수를 올리면 갱신 유실이 생깁니다.
- 클라이언트가 점수 갱신 API를 직접 호출하게 두면 순위표의 신뢰가 무너집니다.
- 동점 정책 없이 `ZRANK` 결과를 공식 순위로 쓰면 보상 분쟁이 생길 수 있습니다.
- Snapshot 중 Copy-on-Write 메모리를 고려하지 않으면 평소에는 충분한 서버가 저장 시점에 죽습니다.

### 오늘의 한 문장

> 실시간 순위표는 매번 정렬하는 시스템이 아니라, 점수가 바뀔 때 순서를 함께 갱신하는 시스템입니다.

### 30초 확인 문제

한 사용자의 점수를 애플리케이션에서 읽어 1을 더한 뒤 다시 저장하는 요청 두 개가 동시에 실행됐습니다. 어떤 문제가 생기며 어떻게 고칠까요?

### 정답과 해설

두 요청이 같은 기존 점수를 읽고 같은 새 점수를 쓰면 승리 한 건이 사라집니다. Redis의 `ZINCRBY`처럼 저장소가 제공하는 원자 증가 연산을 사용해야 합니다. 경기 결과 자체에도 고유 ID를 두고 이미 반영한 결과인지 확인하면 네트워크 재시도로 같은 승리가 두 번 더해지는 문제도 막을 수 있습니다.
