# System Design Daily

## Day 07/40: ID 한 개에도 시간과 위치를 담는다

### 오늘의 질문

충돌 없이 정렬 가능한 ID를 어떻게 만들까요?

데이터베이스 한 대에서는 `auto_increment`가 간단합니다. 여러 데이터센터와 여러 서버가 동시에 ID를 만들기 시작하면 한 숫자를 누가 다음에 가져갈지 합의해야 합니다. 모든 요청을 중앙 데이터베이스에 모으면 고유성은 지키기 쉽지만 그 서버가 병목과 단일 장애 지점이 됩니다.

### WHY: 고유성만으로는 충분하지 않다

ID 요구사항은 서비스마다 다릅니다. 문자열이어도 되는지, 64비트 숫자여야 하는지, 생성 시각 순으로 정렬돼야 하는지, 외부에 노출해도 되는지 먼저 확인해야 합니다.

이번 요구사항은 다음과 같습니다.

```text
64비트 숫자
전역에서 고유
시간 순으로 대략 정렬
초당 10,000개 이상 생성
서버끼리 매번 합의하지 않음
```

고유성만 필요하면 UUID가 좋은 답일 수 있습니다. 하지만 128비트이고 시간 순 정렬이 요구되는 환경에는 맞지 않을 수 있습니다.

### WHAT: 네 가지 선택지

**Multi-master auto increment**는 서버마다 시작점과 증가 폭을 다르게 둡니다. 숫자 ID를 만들 수 있지만 서버 수가 바뀔 때 규칙을 조정하기 어렵고 시간 순서도 보장하지 못합니다.

**UUID**는 각 서버가 독립적으로 만들 수 있어 확장이 쉽습니다. 대신 길고, 숫자 64비트 요구사항을 만족하지 않으며, UUID 버전에 따라 시간 순 정렬 특성도 다릅니다.

**Ticket Server**는 중앙 서버가 다음 번호를 발급합니다. 구현은 단순하고 엄격한 증가 순서를 만들 수 있지만 장애와 처리량이 중앙 서버에 집중됩니다. 구간을 미리 빌려주는 방식으로 호출 수를 줄일 수 있지만 서버 장애 시 사용하지 못한 구간이 생깁니다.

**Snowflake 방식**은 64비트를 여러 구간으로 나눕니다.

```text
1 bit   : sign
41 bits : timestamp in milliseconds
5 bits  : datacenter id
5 bits  : machine id
12 bits : sequence within the same millisecond
```

각 서버는 자신의 데이터센터 ID와 머신 ID를 갖습니다. 같은 밀리초 안에서는 Sequence를 증가시킵니다. 다음 밀리초가 되면 Sequence를 0으로 되돌립니다. 서버끼리 매 ID마다 통신하지 않아도 조합이 겹치지 않습니다.

12비트 Sequence는 서버 한 대가 1밀리초에 `2^12 = 4,096`개를 만들게 합니다. 41비트 Timestamp는 선택한 Epoch부터 약 69년을 표현합니다.

### HOW: 생성보다 운영 규칙이 더 중요하다

ID 생성 과정은 짧습니다.

1. 현재 시각에서 Custom Epoch를 뺍니다.
2. 데이터센터 ID와 머신 ID를 붙입니다.
3. 같은 밀리초의 Sequence를 증가시킵니다.
4. 각 비트를 이동한 뒤 OR 연산으로 64비트 값을 만듭니다.

```text
id = timestamp << 22
   | datacenterId << 17
   | machineId << 12
   | sequence
```

하지만 운영에서는 다음 규칙이 필요합니다.

- 머신 ID를 중복 할당하지 않는 등록 절차
- 한 밀리초에 Sequence를 모두 쓰면 다음 밀리초까지 기다리는 처리
- 시계가 뒤로 갔을 때 생성 중단, 대기, 대체 노드 전환 중 하나를 선택하는 정책
- Epoch 만료 전에 포맷을 바꾸는 마이그레이션 계획
- ID를 외부에 노출할 때 트래픽 규모와 생성 시각이 드러나는지 검토

### 실무 예와 트레이드오프

주문 ID를 Snowflake로 만들면 생성 시각 기준으로 대략 정렬돼 데이터베이스 인덱스의 무작위 삽입을 줄일 수 있습니다. 로그에서도 시간 범위를 빠르게 좁힐 수 있습니다. 반면 연속 ID가 아니므로 누락처럼 보이는 숫자가 정상입니다.

중앙 Ticket Server는 엄격한 순번이 필요한 회계 문서 번호에는 더 적합할 수 있습니다. 이 경우 고가용성, 구간 예약, 중복 발급 방지를 별도로 설계해야 합니다. ID 생성기 하나로 모든 식별자 요구를 해결하려 하면 안 됩니다.

### 실패 모드

가장 위험한 문제는 Clock Rollback입니다. NTP 보정이나 가상 머신 이동으로 시계가 뒤로 가면 과거 Timestamp와 같은 머신 ID, Sequence 조합을 다시 만들 수 있습니다. 일정 범위의 역행은 기다리고, 큰 역행은 노드를 격리하는 식의 정책이 필요합니다.

머신 ID를 설정 파일에 수동으로 적으면 배포 복제 과정에서 같은 ID가 두 서버에 들어갈 수 있습니다. 생성기는 정상처럼 보이지만 충돌이 생깁니다. 머신 ID 임대와 중복 감시가 필요합니다.

### 함정 체크

- "고유 ID"를 듣고 바로 UUID를 선택하지 않습니다. 길이, 타입, 정렬 요구를 확인합니다.
- Snowflake ID가 엄격하게 한 칸씩 증가한다고 기대하지 않습니다.
- NTP만 켜면 Clock Rollback 문제가 사라진다고 가정하지 않습니다.
- 머신 ID 할당을 수동 운영에 맡기지 않습니다.
- 비트 배분을 복사하지 않습니다. 수명, 서버 수, 밀리초당 처리량에 맞춰 조정합니다.
- 외부 노출 ID에서 생성 시각과 사업 규모가 추정될 수 있음을 고려합니다.

### 오늘의 한 문장

> 분산 ID는 숫자를 세는 문제가 아니라, 시간과 생성 주체와 같은 순간의 순서를 겹치지 않게 인코딩하는 문제입니다.

### 30초 확인 문제

Snowflake 생성 서버의 시계가 5초 뒤로 이동했습니다. 그대로 ID 생성을 계속하면 어떤 문제가 생기며, 어떻게 대응할 수 있을까요?

### 정답과 해설

과거에 사용한 Timestamp 구간으로 돌아가 같은 머신 ID와 Sequence 조합을 다시 만들 수 있으므로 ID 충돌 위험이 생깁니다. 시간 순 정렬도 깨집니다.

작은 역행은 마지막 생성 시각까지 기다릴 수 있습니다. 5초처럼 큰 역행은 해당 노드의 생성을 중단하고 정상 시계의 대체 노드로 넘기는 편이 안전합니다. 어떤 정책을 택하든 Clock Rollback 횟수와 중단 시간을 모니터링해야 합니다.
