# System Design Daily

## Day 13/40: 자동완성은 검색이 아니라 미리 계산한 순위다

### 오늘의 질문

- 사용자가 `sys`를 입력할 때마다 전체 검색어를 훑어 인기 상위 5개를 계산해도 될까요?

### WHY: 100ms 안에 계산을 끝내야 한다

자동완성은 키 입력마다 호출됩니다. 검색 한 번보다 요청 수가 훨씬 많고, 사용자는 입력 흐름이 끊기는 지연을 바로 느낍니다. 매 요청마다 접두사와 일치하는 모든 검색어를 찾고 정렬하면 데이터가 커질수록 응답 시간이 흔들립니다.

해법은 읽을 때 계산하지 않는 것입니다. 과거 검색 로그를 집계해 접두사별 상위 후보를 미리 만들고, 온라인 요청은 이미 계산된 결과를 읽기만 합니다.

### WHAT: Trie와 접두사별 Top K 캐시

Trie는 문자열을 접두사 단위로 공유하는 트리입니다. `system`, `syntax`, `sync`는 첫 글자부터 공통 경로를 사용합니다. 기본 Trie에서 `sy`를 찾은 뒤 하위 노드를 모두 순회하면 후보를 구할 수 있지만, 인기순 정렬 비용은 여전히 큽니다.

각 노드에 상위 5개 검색어를 저장하면 조회가 단순해집니다.

```text
key: "sy"
value:
  1. system design, 1_240_000
  2. syntax error, 820_000
  3. sync files, 610_000
```

조회 서비스는 접두사 노드를 찾고 캐시된 목록을 반환합니다. 시간 복잡도는 후보 전체 크기보다 입력 접두사 길이에 가까워집니다. 메모리를 더 쓰는 대신 지연을 안정시킵니다.

### HOW: 쓰기 파이프라인과 읽기 파이프라인을 분리한다

검색할 때마다 Trie를 직접 갱신하면 쓰기 경합이 커지고 순위가 계속 흔들립니다. 원문 설계는 분석 로그를 모아 주기적으로 집계하고 새 Trie 스냅샷을 만듭니다.

1. 검색 이벤트를 append-only 로그에 기록합니다.
2. Aggregator가 기간별 검색 횟수를 합칩니다.
3. Worker가 접두사별 Top K를 계산해 새 Trie를 만듭니다.
4. 검증된 스냅샷을 Trie Cache와 영속 저장소에 배포합니다.
5. Query Service가 새 버전으로 원자적으로 전환합니다.

실시간 유행어가 중요하면 주간 배치만으로 부족합니다. 장기 인기 점수와 최근 증가량을 섞되, 요청 경로에서 전체 구조를 갱신하지 않습니다. 작은 실시간 후보 집합을 별도로 유지한 뒤 정적 Trie 결과와 합치는 방식이 안전합니다.

### 필터와 지역화

자동완성은 사용자가 입력하지 않은 문구를 먼저 보여주므로 안전 필터가 필수입니다. 금지어는 응답 직전 필터링할 수 있지만, 계속 후보에 남아 계산 자원을 쓰게 됩니다. 긴급 차단은 필터 계층에서 처리하고, 다음 스냅샷에서 물리적으로 제거합니다.

언어와 지역에 따라 인기 검색어가 다릅니다. 하나의 전역 Trie보다 국가와 언어별 Trie를 나누면 품질이 좋아지고 샤드도 작아집니다. 알파벳 첫 글자로만 샤딩하면 `s`처럼 인기 접두사에 트래픽이 몰릴 수 있으므로 실제 분포를 기준으로 범위를 다시 쪼개야 합니다.

### 실패 모드와 운영 지표

새 Trie가 잘못 만들어져도 이전 버전으로 즉시 돌아갈 수 있어야 합니다. 배포 버전, 생성 시각, 필터 규칙 버전을 함께 기록합니다. p95 지연, 캐시 적중률, 빈 결과 비율, 오래된 스냅샷 사용 시간, 접두사별 QPS를 확인합니다.

### 함정 체크

- 검색 이벤트마다 Trie 전체를 갱신하면 높은 쓰기 부하와 잠금 경합이 생깁니다.
- 접두사 하위 트리를 매번 순회하면 인기 접두사의 지연이 폭증합니다.
- 첫 글자 기준 균등 샤딩은 실제 검색어 분포를 반영하지 못합니다.
- 캐시만 두고 버전 관리와 롤백을 빼면 잘못된 추천을 빠르게 복구할 수 없습니다.

### 오늘의 한 문장

> 자동완성의 속도는 빠른 검색보다 접두사별 답을 미리 계산하는 데서 나옵니다.

### 30초 확인 문제

주간 Trie를 쓰는 서비스에서 갑자기 시작된 스포츠 결승전 검색어를 5분 안에 노출하려면 전체 Trie를 매 요청마다 수정해야 할까요?

### 정답과 해설

아닙니다. 최근 검색을 짧은 구간으로 집계하는 작은 실시간 후보 저장소를 별도로 둡니다. 조회 시 정적 Trie의 장기 인기 후보와 실시간 후보를 합쳐 점수순으로 반환합니다. 이렇게 하면 안정적인 주 구조를 유지하면서 유행 반영 시간만 줄일 수 있습니다.
