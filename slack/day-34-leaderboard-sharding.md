# System Design Daily

## Day 34/40: 순위표 샤딩은 쓰기 확장과 전체 순위를 맞바꾼다

### 오늘의 질문

- 한 Redis에 순위표가 더는 들어가지 않을 때, 어떤 샤딩 방식이 상위 10명과 내 순위를 덜 망가뜨릴까요?

### 샤딩하면 정렬된 한 줄이 여러 줄로 갈라진다

단일 Sorted Set에서는 모든 사용자가 한 순서 안에 있습니다. 샤딩은 이 전역 순서를 여러 로컬 순서로 나눕니다. 쓰기는 분산되지만 상위 K명과 사용자 순위는 더 이상 한 노드의 연산으로 끝나지 않습니다.

순위표 샤딩은 저장 공간 배분보다 **전역 순서를 어떻게 다시 만들 것인가**가 핵심입니다.

### 선택 1: 점수 범위로 나누기

```text
shard 0: score 0..99
shard 1: score 100..199
...
shard 9: score 900..1000
```

상위 10명은 가장 높은 점수 샤드부터 읽으면 됩니다. 사용자 순위는 자기 샤드 안의 순위에 더 높은 점수 샤드의 사용자 수를 더합니다.

장점은 전역 순위 계산이 비교적 단순하다는 점입니다. 단점은 점수 분포가 바뀌면 특정 샤드가 뜨거워진다는 점입니다. 시즌 초에는 낮은 점수 구간에 쓰기가 몰리고, 오래된 시즌에는 높은 구간에 사용자가 쌓일 수 있습니다. 점수가 경계를 넘을 때 이전 샤드 삭제와 새 샤드 추가도 원자적으로 처리해야 합니다.

고정 점수 범위는 도메인의 최대 점수와 분포를 잘 알 때 적합합니다. 구간을 동적으로 바꾸면 재분배와 라우팅 버전 관리가 필요합니다.

### 선택 2: 사용자 ID 해시로 나누기

```text
shard = hash(user_id) % N
```

사용자가 고르게 분산되어 쓰기와 메모리 균형이 좋습니다. Redis Cluster가 이런 방식에 가깝습니다. 하지만 각 샤드에는 모든 점수대가 섞입니다.

상위 10명을 구하려면 모든 샤드에서 상위 10명씩 받아 최대 `10 x shard_count`개를 병합합니다. 내 전역 순위는 더 어렵습니다. 각 샤드에서 내 점수보다 높은 사용자 수를 세어 합쳐야 하는데 Sorted Set의 기본 rank 연산만으로 다른 샤드의 기준 점수 카운트를 싸게 얻기 어렵습니다.

샤드 수가 늘수록 Scatter-Gather의 네트워크 왕복과 꼬리 지연이 늘어납니다. 가장 느린 샤드 하나가 전체 응답 시간을 결정합니다.

### 어떤 선택이 맞을까

```text
점수 범위 샤딩
- 전역 순위 조회가 중요하다.
- 점수 범위와 분포를 예측할 수 있다.
- 핫 구간을 운영으로 다룰 수 있다.

사용자 해시 샤딩
- 쓰기 균형과 단순 라우팅이 중요하다.
- 상위 K가 작고 조회 빈도가 낮다.
- 정확한 개인 순위 대신 백분위도 허용할 수 있다.
```

원문은 정확한 순위가 중요한 요구에서는 점수 범위 샤딩을 선호합니다. 하지만 절대적인 답은 아닙니다. 상위 100명 전용 작은 전역 집합을 별도로 유지하고 본체는 해시 샤딩하는 혼합 설계도 가능합니다. 이때 전용 집합은 파생 데이터이므로 원본 샤드와 어긋날 때 복구할 방법이 필요합니다.

### NoSQL Write Sharding도 같은 대가를 낸다

DynamoDB 같은 저장소에서 `season#partition`을 파티션 키로, 점수를 정렬 키로 둘 수 있습니다. 파티션 수를 늘리면 쓰기 처리량은 늘지만 조회할 파티션 수도 늘어납니다.

```text
partition = hash(user_id) % P
partition_key = tournament_id + partition
sort_key = score
```

상위 K는 모든 파티션에서 후보를 가져와 병합합니다. 파티션 수는 설정값이 아니라 읽기 지연과 쓰기 처리량의 계약입니다. 실제 점수 분포와 트래픽으로 벤치마크해야 합니다.

### 운영에서 필요한 것

- 샤드별 메모리, QPS, 상위 점수와 사용자 수를 봅니다.
- Scatter-Gather의 전체 지연뿐 아니라 가장 느린 샤드를 추적합니다.
- 라우팅 버전과 재샤딩 상태를 저장합니다.
- 시즌 종료 순위는 불변 스냅샷으로 보관합니다.
- 온라인 순위가 잠시 어긋나도 원본 경기 로그로 재구축할 수 있어야 합니다.

### 함정 체크

- 샤딩이 쓰기를 분산한다고 순위 조회도 자동으로 분산되는 것은 아닙니다.
- 점수 범위 샤딩에서 시즌 초 핫샤드를 놓치기 쉽습니다.
- 해시 샤딩에서 각 샤드의 1위만 모으면 전역 상위 10명을 구할 수 없습니다.
- 샤드 수를 늘릴수록 Scatter-Gather의 실패 확률과 꼬리 지연이 커집니다.
- 정확한 순위가 비싸다면 요구를 백분위로 바꿀 수 있는지 제품과 합의해야 합니다.

### 오늘의 한 문장

> 순위표 샤딩은 데이터를 나누는 일이 아니라, 나뉜 로컬 순서에서 전역 순서를 복원하는 일입니다.

### 30초 확인 문제

8개 해시 샤드에서 전역 상위 10명을 구하려 합니다. 각 샤드에서 몇 명의 후보를 가져와야 안전하며, 왜 그럴까요?

### 정답과 해설

각 샤드에서 최대 10명씩 가져와야 합니다. 전역 상위 10명이 한 샤드에 모두 있을 수도 있기 때문입니다. 각 샤드의 결과를 점수와 동점 규칙으로 병합해 최종 10명을 고릅니다. K가 커지거나 샤드 수가 늘면 전송량과 병합 비용이 `K x shard_count`에 비례해 커집니다.
