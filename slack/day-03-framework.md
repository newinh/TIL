# System Design Daily

## Day 03/40: 설계보다 먼저 합의하라

### 오늘의 질문

좋은 설계보다 먼저 합의해야 하는 것은 무엇일까요?

"뉴스 피드를 설계해보세요"라는 말을 듣자마자 Kafka와 Cassandra를 그리면 대개 꼬입니다. 친구 글만 보이는지, 추천 글도 섞이는지, 최신순인지, 영상까지 다루는지 아직 모르기 때문입니다. 기능과 규모가 달라지면 읽기 전략, 쓰기 전략, 데이터 모델도 달라집니다.

### WHY: 모호함을 제거하지 않으면 정답도 없다

시스템 설계는 주어진 문제의 유일한 답을 찾는 작업이 아닙니다. 요구사항을 좁히고 선택의 근거를 공유하는 작업입니다. 초반 질문을 건너뛰면 서로 다른 문제를 상상한 채 설계를 진행하게 됩니다.

예를 들어 채팅 시스템에서 "메시지를 보낸다"만 합의하면 부족합니다. 일대일 대화만 필요한지, 대규모 그룹을 지원하는지, 오프라인 메시지를 얼마나 보관하는지에 따라 연결 관리와 저장 구조가 달라집니다.

### WHAT: 네 단계가 만드는 산출물

#### 1. 문제와 범위를 합의한다

핵심 기능, 사용자 규모, 지연시간, 일관성, 지원 클라이언트를 묻습니다. 모르는 값은 가정으로 적습니다. 이 단계의 산출물은 기술 목록이 아니라 설계할 문제의 경계입니다.

```text
핵심 기능: 게시물 작성, 피드 조회
규모: DAU 1천만 명
정렬: 최신순
콘텐츠: 텍스트와 이미지
피드 지연 목표: p95 500ms 이하
```

#### 2. 개략 설계를 함께 그린다

클라이언트, API, 저장소, 캐시처럼 큰 상자만 놓고 주요 요청 흐름을 따라갑니다. QPS와 저장량도 이때 계산합니다. 쓰기 흐름과 읽기 흐름이 요구사항을 만족하는지 확인한 뒤 다음 단계로 갑니다.

#### 3. 가장 위험한 부분을 깊게 판다

모든 상자를 같은 깊이로 설명할 필요는 없습니다. URL 단축기라면 키 생성과 충돌, 채팅이라면 연결 관리와 메시지 순서, 뉴스 피드라면 fan-out 전략이 핵심입니다. 실패했을 때 전체 설계를 무너뜨릴 부분을 고릅니다.

#### 4. 한계와 다음 단계를 정리한다

병목, 장애 처리, 데이터 일관성, 관측 방법을 짚습니다. 사용자가 열 배로 늘면 무엇부터 바꿀지도 설명합니다. 새 구성 요소를 추가하기보다 앞에서 한 선택과 남은 위험을 정리합니다.

### HOW: 질문에서 깊이 파기까지 연결한다

45분 인터뷰라면 범위 합의 5분, 개략 설계 10분에서 15분, 깊이 파기 20분, 마무리 5분 정도로 나눌 수 있습니다. 시간표보다 중요한 것은 단계마다 합의를 얻는 일입니다.

뉴스 피드를 예로 들면 다음처럼 연결됩니다.

1. 최신순 피드와 DAU를 합의합니다.
2. 게시물 작성 API와 피드 조회 API를 정의합니다.
3. 쓰기 시점에 친구 피드를 미리 만드는 방식과 읽기 시점에 합치는 방식을 비교합니다.
4. 친구가 매우 많은 사용자의 fan-out 지연을 핵심 위험으로 고릅니다.
5. 큐 지연, 피드 생성 실패, 재처리 방법을 정리합니다.

이 흐름은 실무 설계 회의에도 그대로 적용됩니다. 먼저 성공 기준과 범위를 문서로 고정하고, 큰 흐름에 합의한 뒤, 되돌리기 어렵거나 장애 영향이 큰 선택만 깊게 검토합니다.

### 트레이드오프와 실패 모드

질문을 많이 한다고 좋은 설계가 되지는 않습니다. 핵심 기능과 규모를 확인하지 않고 주변 기능을 끝없이 묻는 것도 시간 낭비입니다. 답이 없는 질문은 합리적인 가정으로 선언하고 진행해야 합니다.

깊이 파기에서 익숙한 기술만 설명하는 실수도 흔합니다. 요구사항의 위험이 쓰기 순서인데 캐시 전략만 길게 설명하면 설계의 핵심을 놓칩니다. 반대로 모든 컴포넌트를 깊게 다루려 하면 정작 중요한 결정이 얕아집니다.

### 함정 체크

- 요구사항을 묻기 전에 데이터베이스와 메시지 큐부터 고르지 않습니다.
- 개략 설계에 대한 합의 없이 세부 구현으로 들어가지 않습니다.
- 모든 상자를 같은 깊이로 설명하지 않습니다. 가장 위험한 경로를 고릅니다.
- 면접관이나 동료가 알아서 이해할 것이라 생각하고 침묵하지 않습니다. 선택 근거를 말합니다.
- 마지막에 새 기능을 추가하지 않습니다. 병목, 장애, 트레이드오프를 정리합니다.

### 오늘의 한 문장

> 시스템 설계는 혼자 정답을 발표하는 시간이 아니라, 불확실한 문제를 함께 좁혀 가는 과정입니다.

### 30초 확인 문제

개략 설계를 그렸는데 읽기 경로와 쓰기 경로가 모두 복잡합니다. 어느 쪽을 깊게 파야 할까요?

### 정답과 해설

요구사항과 위험도가 결정합니다. 읽기 지연시간이 핵심 SLO이고 읽기 트래픽이 압도적이라면 읽기 경로를 고릅니다. 데이터 유실이 치명적이고 쓰기 순서가 중요하다면 쓰기 경로를 고릅니다.

둘 다 설명하려다 둘 다 얕아지는 것보다 하나를 선택하고 근거를 밝히는 편이 낫습니다. 남은 경로는 마무리에서 위험과 후속 검증 항목으로 남깁니다.
