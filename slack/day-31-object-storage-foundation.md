# System Design Daily

## Day 31/40: 객체 저장소는 데이터와 주소록을 분리한다

### 오늘의 질문

- 100PB를 저장하는 서비스에서 객체 본문과 객체 이름을 왜 같은 데이터베이스에 넣으면 안 될까요?

### 왜 객체 저장소가 필요한가

블록 저장소는 빠른 임의 읽기와 쓰기에, 파일 저장소는 디렉터리와 파일 공유에 적합합니다. 객체 저장소는 다른 선택을 합니다. 파일 수정 성능과 계층형 디렉터리를 포기하고, 큰 규모와 높은 내구성, 낮은 단가를 얻습니다.

객체는 보통 한 번 쓰고 여러 번 읽습니다. 수정도 제자리 덮어쓰기가 아니라 새 객체나 새 버전을 만드는 방식으로 처리합니다. 이 제약 덕분에 저장 위치를 바꾸거나 복제본을 늘리는 작업이 단순해집니다.

### 핵심 설계: 본문과 메타데이터 분리

객체 저장소에는 성격이 전혀 다른 두 데이터가 있습니다.

- **객체 데이터**: 이미지, 백업, 동영상처럼 크고 순차적으로 읽는 바이트입니다.
- **메타데이터**: 버킷, 객체 이름, 크기, 체크섬, 권한, 실제 객체 ID처럼 작고 자주 조회하는 정보입니다.

객체 데이터는 데이터 노드에 저장하고, 메타데이터는 별도 데이터베이스에 저장합니다. 사용자는 `bucket/report/2026.pdf`라는 이름으로 접근하지만 데이터 노드는 UUID 같은 불변 객체 ID로 본문을 찾습니다.

이 분리는 두 계층을 독립적으로 확장하게 합니다. 본문 용량이 부족하면 데이터 노드를 늘리고, 객체 이름 조회가 느리면 메타데이터 샤드나 읽기 복제본을 늘립니다.

### 업로드는 어떤 순서로 처리할까

```text
1. API 서비스가 IAM에서 쓰기 권한을 확인한다.
2. 배치 서비스가 저장할 데이터 노드와 복제 그룹을 고른다.
3. 데이터 노드가 본문을 저장하고 다른 장애 영역에 복제한다.
4. 필요한 복제가 끝나면 객체 ID를 반환한다.
5. 메타데이터 저장소가 버킷, 객체 이름과 객체 ID를 연결한다.
6. API 서비스가 성공을 반환한다.
```

본문을 내구성 있게 저장하기 전에 메타데이터를 공개하면 사용자는 이름은 보이지만 다운로드할 수 없는 객체를 만납니다. 반대로 본문 저장 뒤 메타데이터 쓰기가 실패하면 고아 데이터가 남습니다. 후자는 사용자에게 깨진 객체를 노출하지 않으며 나중에 수집할 수 있으므로 더 안전합니다.

다운로드는 반대 순서입니다. 권한을 확인하고 메타데이터에서 객체 ID를 찾은 뒤, 해당 ID의 본문을 데이터 노드에서 읽습니다.

### 데이터 노드 안에서는 어떻게 저장할까

작은 객체마다 운영체제 파일 하나를 만들면 4KB 블록 낭비와 inode 고갈이 생깁니다. 그래서 작은 객체 여러 개를 수GB 크기의 append-only 파일에 연속으로 붙이고 다음 색인을 로컬에 둡니다.

```text
object_id -> file_name, offset, size, checksum
```

각 데이터 노드는 자기 데이터만 조회하므로 이 색인을 중앙 데이터베이스로 보내기보다 로컬 SQLite나 RocksDB에 두는 편이 낫습니다. 중앙화하면 모든 읽기에 네트워크 왕복이 생기고 색인 클러스터가 새 병목이 됩니다.

### 내구성은 복사 개수만으로 끝나지 않는다

같은 랙에 복제본 세 개를 두면 랙 전원 장애 한 번에 모두 잃습니다. 복제본은 랙, 가용 영역, 네트워크 같은 **장애 영역**을 가로질러 배치해야 합니다.

복제는 읽기와 복구가 빠르지만 저장 공간을 많이 씁니다. Erasure Coding은 데이터 조각과 패리티를 나눠 저장해 단가를 낮추지만, 읽을 때 여러 노드에서 조각을 모으고 복원 계산을 해야 합니다. 자주 읽는 객체는 복제, 오래 보관하는 객체는 Erasure Coding을 선택하는 계층형 정책이 실무에서 유용합니다.

디스크가 완전히 죽지 않고 일부 바이트만 손상될 수도 있습니다. 객체와 묶음 파일에 체크섬을 저장하고 읽기, 백그라운드 스크럽 때 검증해야 조용한 손상을 발견할 수 있습니다.

### 실무 예

사진 서비스에서 원본 이미지는 데이터 노드에 세 가용 영역으로 복제하고, `users/42/avatar.jpg`와 객체 ID의 연결은 메타데이터 저장소에 둡니다. 썸네일은 다시 만들 수 있으므로 복제 수를 줄일 수 있습니다. 모든 객체에 같은 내구성 정책을 적용하지 않아도 됩니다.

### 함정 체크

- 버킷 이름의 슬래시는 실제 디렉터리가 아니라 객체 이름의 일부입니다.
- 메타데이터를 먼저 커밋하면 본문이 없는 객체가 목록과 조회에 노출됩니다.
- 복제본 수만 세고 장애 영역을 나누지 않으면 내구성 계산이 무의미합니다.
- 작은 객체를 파일 하나씩 저장하면 용량보다 inode와 임의 I/O가 먼저 고갈될 수 있습니다.
- 객체 목록 조회는 본문 조회와 다른 접근 패턴입니다. 같은 샤딩 키로 둘 다 빠르게 만들 수 있다고 가정하면 안 됩니다.

### 오늘의 한 문장

> 객체 저장소는 큰 바이트와 작은 주소록을 분리하고, 각각의 병목에 맞게 확장하는 시스템입니다.

### 30초 확인 문제

업로드 중 본문은 세 복제본에 저장됐지만 메타데이터 기록이 실패했습니다. API는 무엇을 반환해야 하며, 남은 본문은 어떻게 처리해야 할까요?

### 정답과 해설

업로드 실패를 반환해야 합니다. 객체 이름이 메타데이터에 없으므로 사용자는 이 본문을 조회할 수 없습니다. 저장된 본문은 고아 데이터로 표시하거나 참조되지 않은 객체 ID를 스캔하는 Garbage Collector가 나중에 회수합니다. 메타데이터만 성공시키는 것보다 고아 데이터를 남기는 편이 안전합니다. 전자는 깨진 객체를 사용자에게 노출하지만 후자는 내부 저장 공간만 잠시 사용합니다.
