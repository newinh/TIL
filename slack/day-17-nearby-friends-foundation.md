# System Design Daily

## Day 17/40: 친구 위치는 최신값만 빠르게 흘려보낸다

### 오늘의 질문

- 3초 전 위치와 30초 전 위치가 뒤바뀌어 도착했다면 어느 값을 친구에게 보여줘야 할까요?

### WHY: 주변 매장과 주변 친구는 갱신 속도가 다르다

매장 주소는 자주 바뀌지 않지만 친구 위치는 계속 움직입니다. 1천만 명이 30초마다 위치를 보내면 초당 약 33만 건의 갱신이 발생합니다. 모든 위치를 강한 일관성으로 저장하고 매번 친구 400명의 위치를 DB에서 읽으면 지연과 비용이 커집니다.

화면에 필요한 것은 각 활성 사용자의 최신 위치입니다. 과거 이력은 분석에 필요하지만 실시간 조회 경로와 분리할 수 있습니다.

### WHAT: 최신 위치 캐시와 이력 저장소

WebSocket Server는 모바일 클라이언트와 지속 연결을 유지합니다. 위치 업데이트를 받으면 두 곳으로 보냅니다.

- Redis Location Cache에는 `user_id -> lat, lng, timestamp` 최신값을 저장합니다.
- Location History DB에는 분석과 교통 추정을 위해 이력을 비동기로 쌓습니다.

Redis 항목에 TTL을 둡니다. 예를 들어 10분 동안 새 위치가 없으면 비활성 사용자로 보고 자동 제거합니다. 별도 오프라인 정리 작업 없이도 활성 집합의 크기를 제한할 수 있습니다.

### HOW: 위치 업데이트와 초기 친구 조회

```text
Client
  -> WebSocket Server
  -> latest location cache 갱신
  -> history stream 기록
  -> user channel에 publish
  -> 친구가 연결된 WebSocket Server가 수신
  -> 거리 계산 후 threshold 안이면 전달
```

클라이언트가 처음 연결되면 서버는 친구 목록을 읽고, 활성 친구의 최신 위치를 캐시에서 가져옵니다. 각 위치의 timestamp를 함께 보내야 클라이언트가 오래된 값인지 판단할 수 있습니다. 이후에는 친구 채널을 구독해 변경분만 받습니다.

업데이트가 네트워크에서 순서를 바꿀 수 있으므로 캐시 갱신은 timestamp 조건을 사용합니다. 새 이벤트의 timestamp가 현재 값보다 클 때만 덮어씁니다. 클라이언트가 보낸 시각을 무조건 신뢰하면 잘못 설정된 기기 시계가 최신값을 막을 수 있으므로 서버 수신 시각이나 허용 오차 정책이 필요합니다.

### 배터리와 최신성의 트레이드오프

위치를 1초마다 보내면 화면은 부드럽지만 배터리와 데이터 사용량이 늘고 서버 QPS가 커집니다. 걷는 사용자는 30초 간격으로도 충분할 수 있지만 차량 이동 중에는 더 자주 갱신해야 합니다. 이동 속도, 앱 상태, 배터리 상태에 따라 간격을 조정할 수 있습니다.

모든 원시 GPS 점을 즉시 보내기보다 클라이언트가 짧게 묶어 배치 전송할 수도 있습니다. 단, 친구 화면의 실시간성 목표와 이력 분석용 전송을 같은 주기로 묶지 않습니다.

### 친구 관계와 공개 범위

위치는 민감한 데이터입니다. 친구 ID만 안다고 구독을 허용하면 안 됩니다. 서버가 현재 친구 관계와 위치 공유 설정을 확인해야 합니다. 친구 삭제나 공유 중단 이벤트가 오면 해당 WebSocket Server가 채널 구독을 해제하고 클라이언트에서도 표시를 지웁니다.

### 함정 체크

- 위치 이력 DB를 실시간 최신 위치 조회에 사용하면 쓰기와 읽기가 서로 방해합니다.
- timestamp 비교 없이 마지막 도착 이벤트를 저장하면 늦게 온 과거 위치가 최신값을 덮습니다.
- TTL 없이 활성 사용자 캐시를 유지하면 이미 떠난 사용자 위치가 계속 노출됩니다.
- 친구 관계 변경을 다음 재연결까지 미루면 위치가 더 오래 공유될 수 있습니다.

### 오늘의 한 문장

> 실시간 친구 위치는 모든 이력을 빠르게 읽는 문제가 아니라 활성 사용자의 최신값과 구독 관계를 짧게 유지하는 문제입니다.

### 30초 확인 문제

사용자가 앱을 강제 종료했는데 친구 화면에 25분 동안 계속 근처로 표시됩니다. 가장 먼저 확인할 것은 무엇일까요?

### 정답과 해설

Location Cache의 TTL과 클라이언트 표시 만료 정책을 확인합니다. heartbeat나 위치 업데이트가 일정 시간 없으면 서버 캐시에서 활성 상태를 제거해야 합니다. 클라이언트도 마지막 timestamp가 기준보다 오래되면 표시를 숨겨야 합니다. 연결 종료 이벤트만 믿으면 모바일 네트워크 단절과 강제 종료를 놓칠 수 있습니다.
