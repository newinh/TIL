# System Design Daily

## Day 14/40: 동영상 서비스는 업로드 뒤부터 시작된다

### 오늘의 질문

- 사용자가 1GB 영상을 올렸다면 그 파일을 그대로 모든 기기에 스트리밍해도 될까요?

### WHY: 원본 파일은 재생 제품이 아니다

동영상 서비스는 파일 저장소처럼 보이지만, 업로드된 원본을 바로 재생하면 문제가 생깁니다. 휴대폰, TV, 브라우저가 지원하는 코덱이 다르고 네트워크 속도도 계속 바뀝니다. 하나의 해상도만 제공하면 느린 회선에서는 버퍼링이 생기고, 빠른 회선과 큰 화면에서는 화질을 낭비합니다.

따라서 업로드와 재생 사이에 비동기 처리 파이프라인이 필요합니다. 원본을 안전하게 저장한 뒤 여러 코덱, 해상도, 비트레이트로 변환하고 CDN에 배포해야 합니다.

### WHAT: 제어 경로와 대용량 데이터 경로

API Server는 인증, 메타데이터, 상태 조회를 처리합니다. 실제 영상 바이트는 API Server를 통과시키지 않고 사전 서명 URL을 사용해 객체 저장소로 직접 올립니다. 재생도 CDN이 담당합니다.

```text
Client -> API: 업로드 권한 요청
API -> Client: pre-signed URL
Client -> Original Storage: 원본 업로드
Storage Event -> Transcoding Pipeline
Pipeline -> Transcoded Storage -> CDN
Completion Handler -> Metadata DB 상태 갱신
```

이 분리는 API 서버의 네트워크 대역폭을 보호합니다. 메타데이터 DB에는 제목, 소유자, 처리 상태, 출력 포맷을 저장하고, 대용량 파일은 객체 저장소에 둡니다.

### HOW: DAG로 변환 작업을 나눈다

트랜스코딩은 CPU 비용이 큽니다. 하나의 거대한 작업으로 처리하면 실패 시 처음부터 다시 해야 합니다. 원본을 GOP 경계에 맞춰 조각내고, 작업을 DAG로 표현하면 독립 단계를 병렬 실행할 수 있습니다.

- 영상 인코딩은 해상도와 코덱별로 병렬 처리합니다.
- 오디오 추출, 썸네일 생성, 워터마크 적용은 필요한 선행 작업 뒤에 실행합니다.
- 중간 산출물과 작업 상태를 임시 저장소에 남겨 실패한 단계만 재시도합니다.
- Scheduler는 작업 우선순위와 Worker 사용량을 보고 배정합니다.

업로드도 청크로 나누면 중단 지점부터 재개할 수 있습니다. 각 청크의 체크섬을 확인하고, 서버는 완료된 청크 목록을 기록합니다. 마지막에 전체 객체를 조립한 뒤에만 `uploaded` 상태로 바꿉니다.

### 재생과 비용의 트레이드오프

HLS나 MPEG-DASH는 영상을 작은 세그먼트로 나누고, 플레이어가 현재 회선에 맞는 품질을 선택하게 합니다. CDN은 인기 영상의 세그먼트를 사용자 가까이에 캐시합니다.

모든 영상을 모든 포맷으로 미리 인코딩하면 재생은 빠르지만 저장과 연산 비용이 큽니다. 조회 가능성이 낮은 영상은 기본 포맷만 만들고 요청이 생길 때 추가 포맷을 생성할 수 있습니다. 반대로 인기 영상은 여러 지역 CDN에 미리 배포해 원본 저장소의 egress를 줄입니다.

### 실패 모드

메타데이터를 먼저 `ready`로 바꾸면 CDN 배포가 끝나기 전에 사용자가 재생을 시도합니다. 처리 상태는 `uploading`, `processing`, `ready`, `failed`처럼 명확히 나누고, 필요한 출력물이 모두 확인된 뒤 공개합니다.

같은 완료 이벤트가 여러 번 올 수 있으므로 핸들러는 영상 ID와 출력 프로필을 멱등 키로 사용합니다. 잘못된 원본이나 지원하지 않는 코덱은 무한 재시도하지 말고 복구 불가능 오류로 종료합니다.

### 함정 체크

- 영상 바이트를 API 서버로 중계하면 애플리케이션 계층이 대역폭 병목이 됩니다.
- 트랜스코딩을 한 작업으로 묶으면 일부 실패도 전체 재처리로 이어집니다.
- 업로드 완료와 재생 준비 완료를 같은 상태로 표현하면 깨진 재생 링크가 노출됩니다.
- 모든 영상을 모든 지역 CDN에 미리 복제하면 비용이 사용량보다 빨리 커집니다.

### 오늘의 한 문장

> 동영상 플랫폼의 핵심은 파일 업로드가 아니라 원본을 재시도 가능한 작업으로 바꾸고 재생 가능한 조각으로 배포하는 과정입니다.

### 30초 확인 문제

긴 영상의 4K 인코딩만 실패했고 1080p와 썸네일은 성공했습니다. 전체 파이프라인을 다시 시작해야 할까요?

### 정답과 해설

아닙니다. DAG의 작업 상태와 중간 산출물을 저장했다면 실패한 4K 인코딩 단계만 재시도합니다. 출력 프로필별 상태를 따로 관리하고, 서비스 정책에 따라 1080p까지 먼저 공개할 수도 있습니다. 단, 메타데이터가 실제 제공 가능한 품질 목록과 일치해야 합니다.
