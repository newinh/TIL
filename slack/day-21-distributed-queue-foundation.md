# System Design Daily

## Day 21/40: 파티션이 병렬성과 순서를 결정한다

### 오늘의 질문

주문 이벤트가 초당 수십만 건 들어올 때, 처리량을 늘리면서 같은 주문의 이벤트 순서를 지키려면 큐를 어떻게 나눠야 할까요?

### 왜 분산 큐가 필요한가

생산자가 소비자를 직접 호출하면 두 시스템의 속도와 장애가 묶입니다. 소비자가 느려지는 순간 생산자 요청도 밀리고, 소비자를 배포하거나 확장할 때 생산자까지 영향을 받습니다.

메시지 큐는 둘 사이에 시간 차를 허용합니다. 생산자는 메시지를 기록한 뒤 다음 일을 하고, 소비자는 자기 처리 속도에 맞춰 읽습니다. 갑자기 트래픽이 몰려도 큐가 완충 구간이 됩니다. 다만 큐를 넣는 순간 메시지 순서, 중복, 지연, 재처리라는 새 설계 문제가 생깁니다.

### 토픽은 업무 흐름의 경계다

토픽은 같은 목적의 메시지를 모으는 논리적 이름입니다. 예를 들어 주문 서비스는 `order-events`, 결제 서비스는 `payment-events`에 이벤트를 기록할 수 있습니다.

토픽을 소비자마다 잘게 복제하면 생산자가 소비자의 요구를 알아야 합니다. 반대로 모든 이벤트를 하나의 토픽에 넣으면 스키마 변경과 접근 제어, 장애 격리가 어려워집니다. 토픽은 조직 이름이 아니라 데이터의 수명, 보안, 처리 방식이 같은 흐름을 기준으로 나누는 편이 낫습니다.

### 파티션은 처리량의 단위다

한 토픽의 데이터가 한 서버에 들어가지 않으면 여러 파티션으로 나눕니다. 각 파티션은 append-only 로그처럼 끝에 메시지를 붙이고, 메시지 위치를 offset으로 표시합니다.

```text
topic: order-events
partition 0: offset 0, 1, 2, ...
partition 1: offset 0, 1, 2, ...
partition 2: offset 0, 1, 2, ...
```

파티션은 서로 독립적으로 읽고 쓸 수 있으므로 처리량이 늘어납니다. 대신 전체 토픽의 순서는 사라집니다. 큐가 보장할 수 있는 현실적인 순서는 보통 파티션 내부 순서입니다.

같은 주문의 순서가 중요하다면 `order_id`를 파티션 키로 씁니다.

```text
partition = hash(order_id) % partition_count
```

이렇게 하면 한 주문의 `CREATED`, `PAID`, `SHIPPED`가 같은 파티션에 들어갑니다. 하지만 유명 판매자 ID처럼 특정 키에 트래픽이 몰리면 핫 파티션이 생깁니다. 순서 범위를 좁힐수록 분산하기 쉬워지고, 넓힐수록 병렬성이 줄어듭니다.

### Consumer Group은 일을 나누는 단위다

같은 Consumer Group에 속한 소비자들은 파티션을 나눠 맡습니다. 한 파티션은 한 그룹 안에서 한 소비자에게만 배정해야 파티션 순서를 지킬 수 있습니다.

예를 들어 파티션이 6개라면 소비자 3개가 각각 2개씩 처리할 수 있습니다. 소비자를 8개로 늘려도 2개는 놀게 됩니다. **한 그룹의 최대 병렬성은 파티션 수가 정합니다.** 처리량 계획에서 소비자 수만 늘려서는 안 되는 이유입니다.

서로 다른 Consumer Group은 각자 offset을 가집니다. 결제 집계 그룹과 사기 탐지 그룹은 같은 메시지를 독립적으로 읽고, 서로의 진행 위치에 영향을 주지 않습니다.

### 재배치는 공짜가 아니다

소비자가 들어오거나 나가고 파티션 수가 바뀌면 coordinator가 파티션을 다시 배정합니다. 이 과정을 rebalance라고 합니다. 장애 복구와 수평 확장에 필요하지만, 재배치 중에는 처리가 잠시 멈추거나 같은 메시지를 다시 읽을 수 있습니다.

실무에서는 다음을 함께 봅니다.

- 파티션 수는 예상 처리량과 향후 소비자 수를 기준으로 잡습니다.
- Consumer Group의 lag를 관찰해 생산 속도와 소비 속도의 차이를 확인합니다.
- 처리 시간이 긴 작업은 heartbeat가 끊겨 불필요한 rebalance를 만들지 않게 조정합니다.
- 파티션 키를 바꾸면 같은 키의 과거와 미래 메시지가 다른 파티션에 놓일 수 있음을 고려합니다.

### 실무 예: 주문 상태 변경

주문 이벤트를 전역 순서로 처리하려고 파티션 하나만 쓰면 설계는 단순하지만 확장 한계가 빠르게 옵니다. 주문 간에는 순서가 필요하지 않으므로 `order_id` 단위로만 순서를 보장하면 됩니다.

반면 재고 차감이 상품 단위 직렬화를 요구한다면 `product_id`가 더 알맞을 수 있습니다. 이때 인기 상품이 핫키가 됩니다. 파티션 키는 데이터 모양이 아니라 어떤 상태를 직렬화해야 하는지에서 출발해야 합니다.

### 함정 체크

- 토픽 전체에 순서가 보장된다고 가정하면 안 됩니다.
- 소비자 수가 파티션 수보다 많아도 처리량은 더 늘지 않습니다.
- 파티션 수를 바꾸면 `hash(key) % N` 결과가 달라져 키의 배치가 바뀔 수 있습니다.
- Consumer Group을 복제본으로 오해하면 안 됩니다. 그룹은 소비 진행 상태를 독립적으로 관리하는 논리적 구독자입니다.

### 오늘의 한 문장

**분산 큐의 처리량은 파티션이 만들고, 보장할 수 있는 순서의 범위도 파티션이 제한합니다.**

### 30초 확인 문제

파티션 12개인 토픽을 같은 Consumer Group의 소비자 20개가 읽습니다. 동시에 일할 수 있는 소비자는 최대 몇 개이며, 같은 고객의 이벤트 순서를 지키려면 무엇을 해야 할까요?

### 정답과 해설

최대 12개가 동시에 일합니다. 한 그룹 안에서 한 파티션은 한 소비자만 맡기 때문입니다. 같은 고객의 이벤트에는 `customer_id`처럼 안정적인 파티션 키를 사용해 모두 같은 파티션으로 보내야 합니다. 단, 고객별 트래픽 편차가 크다면 핫 파티션 위험도 함께 검토해야 합니다.
