# System Design Daily

## Day 06/40: 복제본 수보다 읽기와 쓰기의 약속이 중요하다

### 오늘의 질문

가용성과 일관성 사이에서 무엇을 선택해야 할까요?

분산 Key-Value Store의 API는 단순합니다.

```text
put(key, value)
get(key)
```

어려운 부분은 데이터를 여러 서버에 나눠 저장한 뒤에도 이 두 동작의 의미를 지키는 일입니다. 서버가 고장 나고 네트워크가 갈라져도 응답할지, 방금 쓴 값을 모든 읽기에서 보여줄지 결정해야 합니다.

### WHY: 네트워크 단절은 예외가 아니라 설계 조건이다

한 서버의 메모리에 Hash Table을 두면 빠르지만 용량과 가용성에 한계가 있습니다. 여러 서버로 나누면 용량은 늘지만 같은 값의 복제본이 서로 달라질 수 있습니다.

네트워크 파티션이 생기면 모든 노드가 최신 값을 공유하지 못합니다. 이때 두 선택이 생깁니다.

- 일관성을 우선하면 최신 여부를 확인할 수 없는 요청을 거절합니다.
- 가용성을 우선하면 오래된 값을 반환하거나 충돌 가능성이 있는 쓰기를 받습니다.

CAP은 평상시 데이터베이스 제품을 세 글자로 분류하는 표가 아닙니다. 파티션이 발생했을 때 어떤 약속을 포기할지 묻는 도구입니다.

### WHAT: 파티션, 복제, Quorum

Consistent Hashing으로 키 공간을 여러 노드에 나누고 각 키를 `N`개 노드에 복제합니다. 서로 다른 데이터센터에 복제본을 두면 한 지역 장애에도 데이터를 지킬 수 있습니다.

복제본에 읽고 쓰는 수를 다음처럼 정의합니다.

```text
N = 복제본 수
W = 쓰기 성공에 필요한 확인 수
R = 읽기 성공에 필요한 응답 수
```

`N = 3`, `W = 2`, `R = 2`라면 쓰기와 읽기가 최소 한 복제본에서 겹칩니다. 보통 `W + R > N`이면 최신 쓰기를 만날 수 있는 조건을 만듭니다.

`R = 1`은 읽기가 빠르지만 오래된 값을 볼 위험이 커집니다. `W = 1`은 쓰기가 빠르지만 한 노드에만 반영된 값이 장애로 사라질 수 있습니다. 숫자는 성능 설정이면서 일관성 계약입니다.

### HOW: 쓰기 경로와 읽기 경로를 따로 설계한다

쓰기에서는 먼저 Commit Log에 기록해 장애 후 복구할 근거를 남깁니다. 그다음 메모리 구조에 쓰고, 가득 차면 정렬된 파일인 SSTable로 내립니다.

```text
write -> commit log -> memtable -> SSTable
```

읽기는 메모리와 캐시를 먼저 보고, 없으면 Bloom Filter로 어떤 SSTable에 키가 있을 가능성이 있는지 확인합니다. Bloom Filter는 "없음"을 빠르게 판단해 불필요한 디스크 읽기를 줄입니다.

```text
read -> cache/memtable -> Bloom Filter -> SSTable
```

복제본 응답이 다르면 버전을 비교합니다. Vector Clock은 각 노드의 버전 카운터를 기록해 한 버전이 다른 버전의 후속인지, 동시에 갈라진 충돌인지 판단합니다. 충돌이 확인되면 애플리케이션 규칙이나 사용자 선택으로 병합합니다.

### 장애를 견디는 세 가지 장치

**Gossip Protocol**은 노드들이 서로 Heartbeat와 멤버십 정보를 교환하게 합니다. 한 노드의 주장만으로 다른 노드를 죽었다고 판단하지 않고 여러 관측을 모읍니다.

**Sloppy Quorum과 Hinted Handoff**는 원래 복제 노드가 잠시 내려갔을 때 건강한 다른 노드가 쓰기를 대신 보관하게 합니다. 원래 노드가 복구하면 임시 데이터를 돌려줍니다.

**Merkle Tree**는 복제본 전체를 다시 복사하지 않고 다른 구간만 찾습니다. 상위 Hash부터 비교해 차이가 있는 하위 버킷만 동기화합니다.

### 실무 예와 트레이드오프

장바구니는 잠시 오래된 값이 보여도 쓰기를 계속 받는 편이 나을 수 있습니다. 결제 잔액은 오래된 값을 기반으로 승인하면 금전 오류가 생기므로 일관성을 우선해야 합니다. 같은 회사 안에서도 데이터마다 `R`, `W`, 충돌 해결 정책이 달라집니다.

강한 일관성은 공짜가 아닙니다. 더 많은 복제본 응답을 기다리면 지연시간과 장애 시 오류율이 올라갑니다. 가용성을 높이면 충돌 해결과 복구 로직이 복잡해집니다. 무엇을 선택했는지보다 사용자에게 어떤 이상 현상이 허용되는지 먼저 적어야 합니다.

### 실패 모드

Vector Clock을 끝없이 키우면 메타데이터가 커집니다. 오래된 항목을 줄이는 정책이 필요하지만 잘못 자르면 인과관계를 잃을 수 있습니다. 장애 감지가 너무 민감하면 느린 노드를 죽은 노드로 오판해 복제와 이동이 반복됩니다.

Sloppy Quorum으로 쓰기를 계속 받았지만 Hinted Handoff가 실패하면 임시 노드에 데이터가 오래 남습니다. 운영 지표에는 Quorum 실패, 복제 지연, 충돌 수, 복구 대기 데이터, 노드별 디스크 편차가 포함돼야 합니다.

### 함정 체크

- CAP을 평상시 "셋 중 둘"만 고르는 표로 단순화하지 않습니다. 파티션 시 동작을 설명합니다.
- 복제본 수만 정하고 `R`과 `W`를 생략하지 않습니다.
- `W + R > N`만으로 모든 종류의 강한 일관성이 자동 보장된다고 단정하지 않습니다. 버전과 읽기, 쓰기 방식도 맞아야 합니다.
- 충돌을 데이터베이스가 항상 자동으로 올바르게 병합한다고 기대하지 않습니다.
- 장애 감지, 임시 쓰기 보관, 복구 동기화를 한 흐름으로 검증합니다.

### 오늘의 한 문장

> 분산 Key-Value Store의 핵심은 데이터를 여러 벌 두는 일이 아니라, 장애 중 읽기와 쓰기가 무엇을 약속할지 정하는 일입니다.

### 30초 확인 문제

`N = 3`, `W = 1`, `R = 1`인 설정은 왜 빠르고, 어떤 위험이 있을까요? 재고 차감에 그대로 써도 될까요?

### 정답과 해설

쓰기 한 곳의 확인과 읽기 한 곳의 응답만 기다리므로 지연시간이 짧고 일부 노드 장애에도 응답하기 쉽습니다. 하지만 읽은 복제본이 최신 쓰기를 받지 않았다면 오래된 값을 반환할 수 있습니다. 쓰기 직후 해당 노드가 고장 나면 값이 다른 복제본에 퍼지기 전에 사라질 위험도 있습니다.

재고 차감처럼 중복 판매가 치명적인 동작에는 그대로 쓰기 어렵습니다. 더 강한 Quorum, 조건부 쓰기, 단일 순서화 지점 같은 별도 일관성 장치가 필요합니다.
